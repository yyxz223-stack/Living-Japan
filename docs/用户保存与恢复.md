# 用户保存与恢复

你的修改稿保存在当前酒馆账号的服务器文件区。关闭网页、刷新或更新扩展后，仍从这份保存读取。浏览器缓存和扩展安装目录都不是用户稿正本。

## ① 保存正文

编辑后点击保存。只有服务器写入并读回相同内容后，才确认保存完成；失败时保留本次输入与未保存状态。内置原文保持只读，你的修改稿优先生效。

同一正文从地图、地区、资料入口打开，共用同一份修改稿。真实父子地点、不同分店以及一个地点下的不同正文分支分别保存，不能因为名称相同而合并。

内置正文为空的空位可以补写。空白修改稿不能用于停用资料：停用请关本级正文，撤回修改稿请用“恢复内置原文”。恢复只删除当前正文槽的修改稿，不删除其他稿件。

## ② 备份与导入

在用户备份入口导出 JSON，保存到自己方便寻找的文件夹。不用解压，不用双击，也不用放进扩展安装目录。

本工程的完整用户备份包含修改稿、未对应旧稿、自建空位、Living Japan 开关与界面偏好；不包含整套内置正文、地图和全国店面资料。正式 v3.6 的“自定义正文”备份也支持导入，但它原本不含开关、常用地点及界面偏好。

导入时先选择备份文件，看清新增、覆盖、未对应记录和原文变化数量，再确认。确认前不会改当前保存。同一正文槽以导入文件为准；备份里没有的现有稿件继续保留。完整用户备份还会合并其开关、偏好与自建空位。

无法对应当前版本的旧稿会留下，仍包含在下次导出的备份中；不会按相似名字套给另一个地点。若导入预览后又保存了其他内容，请重新预览再确认，避免覆盖刚保存的修改。

## ③ 更新与恢复

扩展更新只更换程序和内置资料，不覆盖服务器中的用户保存。内置原文有变化时保留你的修改稿及原来的原文基准，供你比较。

通过酒馆扩展安装入口从仓库安装的版本可调用酒馆的检查与更新功能。更新完成后先保存或处理未保存输入，再刷新页面应用；通常不用重启酒馆服务器。手工解压复制的版本若没有仓库信息，检查会明确说明不能在线更新，不冒充已经是最新版。

需要恢复个人内容时，在用户备份入口选择升级前的 JSON，先看预览再确认。恢复当前一篇原文与导入整份用户备份是两个操作。

出现保存失败时，先保留编辑框中的内容；服务器可能已经写入但暂时无法读回，不应直接当成“完全没改过”。请将页面提示、操作顺序，以及浏览器控制台中以 Living Japan 开头的相关错误发回。不要发送整份酒馆设置、聊天或登录凭据。

两台设备连到同一酒馆账号时读取同一份服务器保存。已经发现服务器有另一份更新时会停止覆盖；酒馆通用文件接口不提供跨设备原子锁，因此两端在同一瞬间写入的竞争仍须实测，当前不宣称已支持多人实时协作。

## 开发接入接口

- `createUserStore({transport, initialData?, knownSlots?, normalize?})`：创建独立用户存储。`initialData` 可传正式引擎的默认三组数据；`knownSlots` 可为槽映射或接收当前容器并返回槽映射的函数；`normalize` 可注入纯容器规范化函数。
- `await store.load()`：从服务器读入；首次 404 仅建立内存默认值，不自动写服务器。读取失败保留最后一次确认的内存快照。
- `store.read()`：同步返回独立 JSON 快照。
- `await store.update(mutator, {expectedRevision?})`：串行执行读服务器、检查此前快照、修改副本、增加 revision、写入、读回核对；mutator 可原地修改或返回新容器。失败不提交本地缓存，不触发保存成功通知。调用方必须保留未保存编辑内容。
- `store.subscribe(fn)`：成功载入、成功保存后通知，返回取消订阅函数；监听器异常不会反过来把已经确认的保存当成失败。
- `store.setKnownSlots(slots)` / `store.setNormalizer(fn)`：更新当前内存规范，不直接写服务器。动态槽注册后可把原来未对应的稿重新识别到其准确槽位。
- `store.exportBackup()`：返回完整用户备份 JSON 字符串。
- `store.importBackup(value)` / `store.previewImport(value)`：同步校验与预览，不写服务器。返回 `{format, summary, baseRevision}`；summary 包含 `added/overwritten/unresolved/baseChanged/imported/customSlotsAdded/customSlotsOverwritten/settingsIncluded`。
- `await store.applyImport(preview)`：必须传上一步同一个预览对象；UI确认后调用。如果预览后的保存版本变化，拒绝应用并要求重新预览。
- 错误的 `code`：`NOT_LOADED`、`SAVE_CONFLICT`、`READBACK_MISMATCH`、`READ_FAILED`、`WRITE_FAILED`、`INVALID_DATA`、`INVALID_BACKUP`、`UNSUPPORTED_VERSION`。网络及 JSON 解析错误可能由底层直接抛出。

用户容器保留 `productId/schemaVersion/livingJapanSettings/livingJapanTextOverrides/livingJapanUIPreferences/customSlots`；新增 `storageVersion: 1` 与内部 `revision`。`schemaVersion`继续兼容旧引擎，不用于区分新文件格式。修改稿仍使用 `P/包ID`、`V/旬段ID/包ID`，记录原文hash不因升级改写。

`customSlots`使用稳定空位ID到元数据的映射。由正式引擎提供 `userPackageId(id)`，自建正文仍放在 `livingJapanTextOverrides.records['P/' + userPackageId(id)]`。存储不决定激活词、行政归属或同名合并。动态槽先注册到引擎，再把引擎完整槽映射交给存储；未注册的稿可暂留未对应区，注册后重新规范化即可。

`createSillyTavernTransport({context, fetcher?, filename?})`提供异步`read()/write(value)`。默认文件名`living-japan-user-data.json`，读取`/user/files/…`，写入调用宿主`/api/files/upload`，使用宿主`getRequestHeaders()`。写入返回成功之后仍由store另行读回核对；不存在文件返回null，其余错误不吞掉。真实位置在酒馆当前用户数据区的`user/files/`下，不在扩展Git目录。预览应传本地隔离transport，不调用真实酒馆接口。

`createUpdateManager({context,fetcher?,extensionName?,global?})`默认扩展目录名`Living-Japan`、当前用户安装。`check()`调用`/api/extensions/version`，返回`supported/available`及宿主版本信息；`update()`调用`/api/extensions/update`，返回`reloadRequired`及宿主结果。全局安装由集成入口正确传`global:true`，权限由酒馆处理；不尝试改权限或退回另一个安装目录。更新管理器不持有store，不清浏览器存储，不重写用户文件，不自动刷新页面。

`inspectBuiltinChanges(container,manifest)`只比较正文槽hash，返回`dataVersion/changedSlotKeys/missingSlotKeys`，不修改容器。传入含用户动态槽的当前完整槽表可避免把自建槽误报为缺失。
